# ワークフローの入口（対象を選ぶ）

## 対象の決め方

1. 引数で決める：`blade`（または Blade of Lumia・ゲーム・マップ・敵など）→ **Blade of Lumia**。`site`（または サイト・ブログ・記事・管理画面・smallisle・Vercel・Neon）→ **Small Isle サイト**。
2. 引数が無ければ、同じセッションで直前まで進めていた方を続ける。
3. それでも決まらなければ、どちらを進めるかをユーザーに1回だけ聞く（推測で始めない）。

## オプション：`check`（再開できるかの確かめ・作業はしない）

`/workflow check`（`/workflow blade check`・`/workflow site check` も可）＝**次のセッションで `/workflow` したときに、想定どおりの所から再開できるか**を確かめる。セッションを区切る前に使う（2026-11-15 ユーザー依頼「次に /workflowしたら想定通りのところから再開できるのかサブエージェントとかで確認して欲しい。またこのような確認をするための/workflowのオプションをつけて欲しい」）。

1. **今のセッションの「想定する再開地点」を1〜3行で書き出す**（例：「PLAN キュー108 の『世界が戻る場面の浄化』を作る。最初の一手＝5画面ぶんの塗り替えを作って見せる」）。これは比べる答え＝サブエージェントには渡さない。
2. **会話の文脈を持たない新しいサブエージェント**（`subagent_type` は `general-purpose` か `Explore`・`fork` は使わない＝文脈を引き継いでしまう）を1つ起動し、次だけを頼む：
   - 「あなたは新しいセッションで `/workflow`（対象＝blade か site）を実行した Claude です。`.claude/skills/workflow/SKILL.md` の手順どおり、まず WORKFLOW.md を全文読み、そこから指示される PLAN.md／PROGRESS.md 等を読んで、**次に何をするか**を決めてください。**ファイルの編集・コミット・テストの実行はしない**（読むだけ）。答え＝①どのタスク（PLAN のキュー番号と見出し）②最初の一手（具体的に）③着手の前にユーザーへ聞くつもりのこと④読んで迷った所・記述が食い違っていた所。」
3. サブエージェントの答えを 1. の想定と突き合わせ、ユーザーに報告する：
   - 一致 → 「再開できる」と書く。
   - ずれ・迷い・食い違いがある → **原因の記述（PLAN の再開地点・PROGRESS の現在地・キューの順など）をその場で直し、もう一度サブエージェントで確かめる**（直したことを報告に含める）。
4. `check` は作業を進めない。コミットもしない（直したドキュメントは、ユーザーに確認してからコミットする）。

## Small Isle サイトの場合

1. **まず `site/WORKFLOW.md` を全文 Read する**（毎回。記憶に頼らない）。
2. その手順（Step 1〜5）に従って進める。進み具合の記録は `site/DESIGN.md` §10。
3. サイトの作業は段ごとにコミットしてよい（push はしない）。下の Blade of Lumia の「コミットしない」「Step 5 の3点」はサイトには当てはまらない。

## Blade of Lumia の場合

以下の手順に従う。

### Blade of Lumia ワークフロー実行

このスキルは `outputs/blade-of-lumia/WORKFLOW.md` の runbook に従って開発を進めるためのもの。

#### 手順

1. **まず `outputs/blade-of-lumia/WORKFLOW.md` を全文 Read する**（毎回必ず読む。内容が更新されている可能性があるため記憶に頼らない）。
2. WORKFLOW.md に書かれたフロー（デフォルトフロー / 分岐フロー）に従って進める。
   - ユーザーから特に指定がなければ「🟢 デフォルトフロー：次タスクを進める」を実行する。
   - ユーザーがレビュー・バグ報告・アイデア相談など特定の指示をしている場合は、該当する「🔀 分岐フロー」を実行する。
3. WORKFLOW.md が参照する関連ファイル（`PLAN.md` / `PROGRESS.md` / `DECISIONS.md` / `IDEA.md`）も WORKFLOW.md の指示に従って読み書きする。これらは `outputs/blade-of-lumia/` 配下にある。

#### 注意

- WORKFLOW.md の指示が常に優先される。このファイルは「WORKFLOW.md を読んで従え」という入口にすぎない。
- コミット操作は実行しない（WORKFLOW.md の規定どおり、メッセージ案の提示まで）。
- `git` を使うときは `git --no-pager ...` を付ける。

#### ⚠️ Step 5 の完了報告で必ずやること（抜け防止）

完了報告には **必ず** 以下の3つすべてを出力する。1つでも欠けたら Step 5 未完了。

1. **試し方ガイド（動作確認手順）**：起動方法（`cd outputs/blade-of-lumia && npm run dev`）＋**確認 URL**（`fromEditor=1` の具体的なプレビュー URL を対象画面ごとに列挙）＋**操作手順**（どのキーで何が起きるか・何を見れば正しいと分かるか）。
   - **必須の条件＝「ユーザーの目に見える変化が1つでもあるか」**。マップデータの直し・絵の差し替え・UI・機構、どれも対象＝**「新機能ではないから省く」は禁止**（2026-09-12 ユーザー指摘＝この抜け道で繰り返し省いていた）。
   - 画面に出る変化が本当に無い場合（テストだけ・ドキュメントだけ）は **「画面に出る変化なし」と明記する**（黙って省かない）。
   - サーバを使うなら**配信中のデータが最新か裏取りしてから URL を出す**（[[blade-stale-vite-server-fakes-green]]＝古いサーバが古いデータを配る）。
2. **コミットメッセージ案**（git status から始めて英語 prefix 付き）
3. **次タスクの推奨モデル**：`PLAN.md` の次タスク見出しの 🧠/⚡/🧠→⚡ を読んで、以下の形式で出力する：
   > 次は **Phase X-Y（タスク名）**。推奨モデルは **◯◯**（理由）。
   - 🧠→⚡ で設計が PLAN.md/DECISIONS.md に書き出し済み → ⚡ Sonnet
   - 🧠→⚡ で設計が未着手 → 🧠 Opus
   - ユーザーに「PLAN.md を見てください」と丸投げしない。自分で読んで判断して出力する。
