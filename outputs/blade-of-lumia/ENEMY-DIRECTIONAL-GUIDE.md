# 陸上敵の directional 機構（向き別スプライト・攻撃・ガード）実装ガイド

skeleton（骸骨剣士）で確立した「向き別スプライト＋剣攻撃＋実効ガード」の機構をまとめる。
残り14種の陸上敵（5.5k）を実装するときは、**着手前に必ずこの文書を読む**。
機構自体（`ENEMY_META.directional` フラグを立てて `attack.type:'sword'` を設定すれば動く）は
skeletonで完成済みなので、新しい敵は基本的にデータ追加だけで済むはず。ここに書く罠を踏まなければ
①エンジン基盤の実装は速い（今回は手戻りに時間を使った・後述）。

初出＝2026-08-10（5.5k・skeletonの①エンジン基盤＋ガード実効化＋②量子化共通スケール化）。
関連＝`SPRITE-PIPELINE.md`（スプライト生成・量子化の手順書）／DECISIONS.md 2026-08-10 各エントリ。

---

## 1. 機構の全体像

- `shared/enemies.js` の `ENEMY_META[TILE]` に `directional: true` を立て、`attack: { type: 'sword', range, cooldown }` を設定すると、以下が自動で有効になる（`game/enemy-ai.js`）：
  - **向き別スプライト解決**＝`resolveEnemySprite(e, meta, now)`。`${base}${Dir}`（通常）／`${base}${Dir}Atk`（攻撃中）／`${base}${Dir}Guard`（ガード中）を返す。`base` は `meta.sprite` から `D/R/L/U/Atk/Guard` サフィックスを剥いた名前。
  - **向き差替の同期**＝`syncDirectionalSprite(e, meta)`。`enemyTick()` が directional な敵だけ毎tick呼ぶ（DOM の canvas を差し替える）。
  - **ガードの状態機械**＝`tickGuard(e, meta, now)`。後述。
- `directional:true` を持たない既存敵（patrol/chaser/sentry や各ボス）は影響を受けない（後方互換・従来の `e.sprite` 固定＋flipX のまま）。

## 2. スプライト命名規則（実データが必要な組み合わせ）

`base` を敵の基本名（例 `skeleton`）とすると、必要なスプライト名は：

```
{base}D  {base}R  {base}U        … 通常（Lは無し。既存 dirSuffix マップ〈left→'R'〉どおり R を flipX して代用）
{base}DAtk {base}RAtk {base}UAtk … 攻撃ポーズ
{base}DGuard {base}RGuard {base}UGuard … 構えポーズ
```

`shared/sprites-enemies.js` にこれら9個を登録する（`ENEMY_SPRITES.xxx = ...`）。**それぞれの絵が満たすべき条件（構えは歩行と見分けられること・同じ物体は全方向で同じシルエット・向きで変わるのは正面の向きと重なりだけ）は §6。****まだ向き別の実描画が無い段階では、既存ボスと同じ「参照エイリアス」方式で先に機構だけ通す**（例：`ENEMY_SPRITES.skeletonR = ENEMY_SPRITES.skeleton`）。エイリアスは後で実データに差し替えれば済む＝データとエンジンの検証を分離できる（skeletonでもこの順で進めた）。

## 3. ガードの実効化（★最重要・最初の実装で見た目だけにしてダメ出しされた）

**ガードは見た目の演出ではなく、実際にダメージを無効化する機構にする。** 初回実装で見た目（`_guardUntil` の窓だけ）にしてユーザーに「防御全然してくれない」と指摘された。正しい設計：

- ガード中は**①移動しない②攻撃しない③向きをロック**（ガード開始の瞬間だけ `e.dir` を確定し、以後プレイヤーが動いても向き直らない）。
- ロックした向きから見て**攻撃者がその方向にいるときだけ無効化**（`game/combat.js isGuardBlockingDir(e, srcX, srcY)`）。側面・背後からは通常どおり通る＝プレイヤーが回り込む戦略が意味を持つ。
- **ブーメラン命中は常にスタン＋ガード強制解除**（`game/projectile.js`）。ダメージが正面ブロックされてもスタン効果は貫通する＝「ブーメランで動きを止めてガード不能にしてから殴る」がプレイヤー側の攻略手段になる。

実装箇所：
- `game/enemy-ai.js tickGuard(e, meta, now)` — ガード状態機械。戻り値 `true` ならその tick の `enemyChase`/`enemyAttack` を丸ごとスキップする（`enemyTick()` 側で分岐）。
- `game/combat.js isGuardBlockingDir(e, srcX, srcY)` — 攻撃発生源座標から見た方向とロック方向が一致するか判定。`dealDamageToEnemy()` の無効化チェック列に入る（`meleeOnly`/`submerged` と同じ漏斗）。
- ダメージを与える全ての呼び出し元（剣・矢・ブーメラン・貫通弾・ロウソク）が **攻撃発生源の座標（`srcX, srcY`）を `dealDamageToEnemy()` に渡す**必要がある。新しい攻撃手段を敵に追加するときは、この配線を忘れない。

### 3-1. ★ guardRange の罠（ここで一番時間を溶かした）

`tickGuard` の「ガードに入る距離」（`guardRange`）は、**プレイヤーの攻撃が実際に届く距離（`SWORD_REACH` や `sword.range`）と一致させる**。

最初の実装は「見た目だけの威圧」用に `guardRange = sword.range * 1.6`（射程より広い）にしていた。これを実効化しても直さなかったため、**ガード中の敵は常に剣の射程外にいる**状態になり、「ガード判定を有効にしても無効にしても、そもそも当たっていないので hp が変化しない」という**歯のないテスト**を書いてしまった（潰しても緑のまま＝何も検証していないのに気づかず進めてしまった）。

**チェックリスト**：
1. ガード開始距離とプレイヤーの攻撃到達距離を数値で比較する（`guardRange <= sword.range` になっているか）。
2. 「歯の確認」（判定コードを一時的に `if (false && ...) ` で潰して赤くなるか）をやる前に、**まず判定を有効にした状態で実際にダメージが変化する筋（＝当たっている）を1つ実機で確認してから**、無効化ロジックを検証する。当たってもいないのに「潰しても緑」を「機構が正しい証拠」と誤読しない。

### 3-2. ★ 敵と同じタイルへプレイヤーは進入できない（回り込み経路を作るときの制約）

`game/passable.js isPassable()` は「敵と同じタイルセルへの進入」を重なり防止でブロックする（大型敵は占有セル全部）。**ガードで位置固定された敵の真横（同じ行・同じ列）を直接すり抜けて反対側へ回り込むことはできない**。テストやレベルデザインで「側面/背後に回り込む」経路を作るときは、敵の周囲1マス以上离れた迂回路を用意する（内側の通路を使う・南北どちらかにオフセットするなど）。これに気づかず「動くはずの movePlayer が3回目だけ動かない」と何度も経路を変えて試行錯誤した。

## 4. テスト実装の注意点

- `game/game.js getEnemiesSnapshot()`（`__game.getEnemies()` の実体）に、新しい状態を観測するフィールドを追加する（`dir`/`sprite`/`atkUntil`/`guardUntil`/`guarding`/`guardDir` は既に追加済み）。新しい状態を作ったら同じ要領でここに追加してからテストを書く。
- **`animFrame`（歩行アニメの2フレーム目切り替え）は実時間の `setInterval`（`shared/sprites.js startAnimLoop`・400ms）で進む。`__game.step(n)`（論理時間）では進まない。** 見た目のフレーム切り替えを確認したいときは `page.waitForTimeout(450)` のように実時間を待つ（`.scratch/shot-skel-walk2.mjs` が実例）。
- 「歯の確認」をする前に、まず判定を有効にした状態で実機ログ（`.scratch/` の使い捨てスクリプト）を取り、対象の値（hp・座標・フラグ）が期待どおり変化する1本の筋を先に固める。それから無効化して赤くなることを確認する（§3-1 と同じ理由）。

## 5. 新しい敵を追加するときの手順（まとめ）

1. `shared/enemies.js` の `ENEMY_META` に `directional:true` を立てて追加（既存の脅威度・攻撃タイプ定義はそのまま）。
2. `shared/sprites-enemies.js` に9個のスプライト名を登録（最初はエイリアスで良い＝§2）。
3. 攻撃タイプが `sword` 以外（分裂・突進・遠隔等の新機構）を持つ敵は、`tickGuard`/`resolveEnemySprite` がそれらの攻撃タイプにも対応しているか確認する（現状は `sword` 前提の実装＝新しい機構を足すときはこの前提を崩さないよう分岐を追加する）。
4. `guardRange` を実際の攻撃到達距離と一致させる（§3-1）。
5. ダメージを与える新しい攻撃経路を作るなら、`srcX, srcY` を `dealDamageToEnemy()` に渡す配線を忘れない（§3）。
6. 実機で「当たる筋」を先に1本確認してから、テスト＋歯の確認を書く（§3-1・§4）。
7. スプライトを実データにする際は `SPRITE-PIPELINE.md` の手順＋`quantize-shared.mjs`（複数フレームは必ずこれ・§3-★参照）を使う。**絵の内容そのものの作法は §6（機構と絵の対応）を先に読む。**

## 6. 向き別の絵の作法（★機構と絵の対応・2026-08-11 #8 骸骨剣士でユーザー指摘を4回受けて確定）

**作り方の手順は `SPRITE-PIPELINE.md`（§6 が確定手順）。ここに書くのは「機構の側から絵に要求されること」＝ツールを正しく使っても間違える種類の誤り。** #8 では「12枚できた・543 passed・完了」と報告した後に**4件**の誤りをユーザーが見つけた（＝機械検査が全緑でも絵の意味は検証されない）。同じ手戻りを14種で繰り返さないため原則を残す。

### 6-1. ★ ポーズの絵は「機構の状態をプレイヤーに読ませる」責務を持つ＝見分けられなければ機構が壊れているのと同じ

ガードはロックした向きからの攻撃だけ無効化する（§3）∴**プレイヤーは「今この敵は構えている・正面は無効」を絵から判断する。** ∴構えの絵は歩行・攻撃と**一目で区別できる**必要がある（同じ理由で攻撃の絵も区別できる必要がある）。#8 の UP 構えは初版が「歩行と同じ位置に盾がある」状態で、機構は動いているのにプレイヤーには何も伝わらなかった。**確定＝構えは「盾を持ち上げて体側へ寄せ一段大きくする」（DOWN で確定した差分）を全方向で当てる。** 差分が小さいと感じたら実機の16枚シート（§6-4）で歩行と並べて見る。

### 6-2. ★★ 同じ物体は全方向で同じシルエット（形・寸法）を保つ。向きで変わるのは「正面の向き」と「重なり」だけ

#8 の UP の盾で**2回**間違えた：①RIGHT の側面バンド（細い縦帯）をそのまま流用した＝上を向いているのに盾の側面が画面右を向く絵／②作り直したら長方形の板にした＝DOWN の盾は凧形（平らな上辺＋直線の側辺＋下端が尖る・9幅×15行）なのに**同じ盾に見えない**。

**確定した導出順序（1つでも飛ばすと上のどちらかを踏む）：**

1. **その向きで「正面」がどこを向くかを決める。** 構え＝**向いている方向へ盾の正面を向ける**（DOWN=正面が画面手前／RIGHT=画面右／UP=画面奥）。
2. **カメラから見える形を決める。** 正面が手前 or 奥＝**全形（凧形）が見える**（奥向きは裏面を見るだけでシルエットは同じ）／正面が画面左右＝**側面バンド**。
3. **重なりを決める。** 正面が奥（UP）のときだけ**盾は体より奥**∴骨が手前に描かれ、盾は肋骨の隙間から覗く。
4. **位置は既に確定した方向の値を「体の中心で鏡像」にして出す。** ⚠️ **「DOWN の盾は体の横に構えているから全形が見える」は誤り（ユーザー訂正）＝正面に構えているから全形が見える。画面上で左寄りなのは腕の側だからにすぎない**∴左右位置は腕の側とともに反転する（#8＝体x9-23 に対し UP の盾は x20-28）。
5. **歩行→構えの差分も同じものを鏡像で当てる**（§6-1）。

**★ 形は「採用済みフレームのグリッド」から取る＝自分の思いつきで描かない。** ①も②も、既に採用済みの `skeletonGuard` のグリッドを見て形を取っていれば起きなかった。

### 6-3. ★ 絵の根拠はエンジンの実装から取る（好み・直前のレシピの一般化で決めない）

盾の見せ方は**プレイヤー側の実装が既に答えを持っている**＝`game/render-chars.js` の待機時：**down は正面の `shield` を体の前（z-index 4）／right・left は `shieldSide`（細い側面帯）／up だけは `shield` を z-index -1＝体の裏**。**「上向きだけ盾を体の裏に描く」というこのコードが §6-2 の 2・3 の裏取りそのもの。** 誤り①の原因は「直前に RIGHT で決めたレシピを『ガードの形』として一般化した」＝向きごとに導出し直す手間を飛ばしたこと。**新しいポーズを作るときは、対応する見た目がプレイヤー側か既存敵に既に有るかを先に探す。**

### 6-4. ★ 検証の作法（機構の時間窓があるので「意図」でラベルを打つと必ず取り違える）

- **★★ スクショのラベルは意図（歩行1/歩行2/ポーズ）でなく `k.sprite` の実名から作る。** 敵に寄れば `_atkUntil`/`_guardUntil` は勝手に立つ∴歩行の枠に構えの絵が入り、ポーズ枠には**先に立った窓**しか写らない。#8 の初版はこれで「歩行2が攻撃に見える／ポーズが歩行1と同じ」という読み違いを生んだ。
- **攻撃窓と構え窓は別々に待って両方撮る**（4方向×4ポーズ＝16枚）。
- **盤面が出たら即 `pause()`。** `test_mechanics 0,0` は 12×10・skeleton は (5,3)＝**上/下からの接近は距離2しかない**∴数百ms 走らせると素の歩行が一度も撮れない（左右は距離4で間に合う＝**症状が方向で違うので「UP のスプライトが壊れている」と誤診しやすい**）。
- **`animFrame` 待ちで `resume()` しない。** 400ms の `setInterval`（`shared/sprites.js`）はゲームループと独立に進み **pause 中も再描画される**∴実時間を待つだけでよい。
- **実機シートとは別に「登録データを名前どおり並べるだけ」の図も見る**（`.scratch/shot-skel-frames.mjs`＝`shared/sprites-enemies.js` を import・各フレームの不透明行数も出す）＝時間窓に一切依存せず名前とデータを突き合わせられる。
- **★ left の反転は `getComputedStyle(canvas).transform` では検出できない**＝`makeSprite(name,pal,true,flipX)` が**ピクセルに焼く**∴目視で判定する。

### 6-5. ★ 判定を自分でやる（絵の欠陥をユーザーに見つけさせない）

- **見せる前に自分で画像を見て、明らかな欠陥を潰す**（身長/接地の不揃い・向きの矛盾・要素の欠落・同じ物体の形の不一致）。#8 では歩行2の差分が8ドットしか無い（片足1行）欠陥は自分で見つけて2行＝17ドットに直せたが、盾の形の不一致は3回ユーザーに指摘された。
- **数えられるものは数える**（不透明行数で身長・差分ドット数で歩行・重心で鏡像）。#8 では left/right の構えが非対称に見えたが赤の重心を測ると cx 7.9 対 23.1 ＝厳密な鏡像だった＝**目視の違和感は測って切り分ける**（測らずに直すと正しい物を壊す）。
- **「完了」と言う前に、①登録データ直並べの図と②実機16枚の図の両方を自分で見る。** テストが全緑でも絵の意味は検証されない（#8 の 543 passed は4件の誤りを1つも捕まえなかった）。

## 7. 行動 AI の作法（★2026-08-12 #7 剣獣がユーザー実プレイで「だめだね」と返ってきて確定）

**向き別スプライトと攻撃が動く≠敵として成立している。** #7 剣獣は機構・絵・部屋の組み直し・552 passed まで通した後、実プレイで5点まとめて否定された（①攻撃中も動く ②追従が完璧すぎて逃げ切れない ③複数体で倒せない ④遠隔攻撃を一度も撃たない ⑤遠隔を持つのに1セルまで詰めてくる）。原因は独立な3つで、いずれも**残り14種でそのまま再発する種類**なので機構として一般化した。

### 7-1. ★ 攻撃硬直＝`meta.attackFreezeMs`（プレイヤーとの対称性で決める）

- プレイヤーは攻撃ポーズ中に動けない（`game/player.js` の `if (p?._atkUntil != null && gameNow() < p._atkUntil) return;`）。**敵に同じ窓が無いと「斬りながら追ってくる」＝プレイヤー側だけが不利なルールになる。**
- `markAttack(e, meta, i, now)`（`game/enemy-ai.js`）が**クールダウン記録・`_atkUntil`（絵のポーズ）・`_freezeUntil`（移動禁止）を1か所で立てる**。新しい攻撃タイプを足すときは `e._attackTimes[i] = now` を直接書かず**必ず `markAttack` を通す**（6か所に散っていたのを統合した＝直書きすると硬直が抜ける）。
- 既定値は `directional ? ATTACK_POSE_MS : 0`＝**既存の非 directional 敵の挙動は変わらない**。硬直を長くしたい敵だけ `attackFreezeMs` を書く（剣獣は 360ms＝3 tick）。

### 7-2. ★★ 敵の速度をプレイヤーと同速にしてはいけない

`ENEMY_SPEED_FAST = 1.0` はプレイヤーと**完全同速**（プレイヤーも `processHeldKeys` で毎 tick `speed 1.0` を積んで `MOVE_STEP 0.5` 動く）。**同速の敵は真っすぐ逃げても間合いが1ミリも開かない**＝「逃げ切れない」。速い敵を作るときも `ENEMY_SPEED_FAST * 0.85` のように**プレイヤーより必ず遅くする**（追いつけない相手を作りたいなら速度ではなく突進・瞬間移動のような別機構で表現する）。

### 7-3. ★★ 遠隔攻撃を持つ敵は「近づくモード」と「遠隔モード」を分ける＝`meta.combat`

- 常に `enemyChase` だと**密着し続ける∴遠隔攻撃の `minRange` に一度も届かず発火しない**（剣獣の `swordBeam` は `minRange 2.5`）。プレイヤーから見れば「遠隔を持っているのに常にくっついてくる」＝キャラの設計が消える。
- `meta.combat = {keepMin, keepMax, rangedMs, meleeMs, startMode}` を書くと `tickCombatMode()` が二相を交替させる。遠隔相は `enemyKeepDistance()`（`keepMin` より近ければ**退がる**／`keepMax` より遠ければ寄る／間なら**行・列を揃えて撃つために止まる**）、近接相は従来の `enemyChase()`。**`combat` を書かない敵は今までどおり。**
- **`keepMin` は遠隔攻撃の `minRange` より外に置く**（剣獣は minRange 2.5 に対し keepMin 3.0）。ここがずれると「遠隔モードなのに撃てない位置に居る」状態になる（§3-1 の guardRange と同じ型の罠）。
- **交替は乱数にせず `e.id` から決定的に位相をずらす**（`phaseOffsetMs`）。理由＝(1) 同種を複数置いたとき一斉に突っ込むと「囲まれて袋叩き」に戻る (2) 乱数はテストが不安定 (3) プレイヤーがリズムを読める。

### 7-4. ★ 行動 AI を測るテストの落とし穴（4つとも実際に赤くして直した）

- **観測フィールドを先に通す。** `__game.getEnemies()` = `getEnemiesSnapshot()` は**ホワイトリスト**∴`e._cmode` のような内部フィールドは**テストから常に `undefined`**（assert が静かに空虚になる）。新しい状態を作ったら §4 のとおりまずここへ追加する。
- **「硬直中は動かない」は tick の境目で1つずれる。** `gameTick` は「移動 → `enemyAttack`（ここで初めて `_freezeUntil` が立つ）」の順∴**攻撃した tick 自身は期限を持つが既に移動済み**。判定は「直前 tick の期限」と「この tick の `now`」で行う。
- **ユークリッド距離だけ見ると「逃げているのに縮む」。** 遠隔相で敵が縦に退がっていると、近接相でその縦のずれを食いながら追ってくる（実測 3.0→2.12）。逃走の測定は**密着（近接相・dist ≤ 1.5＝食えるずれが無い状態）まで待ってから**始める。
- **モードごとの間合いは切替直後には測れない**（近接相の終わりは 1.0 に居る∴`keepMin` まで退がるのに5〜8 tick かかる）。切替から10 tick 以上経った落ち着いたサンプルだけを見る。
- **検証ステージは遮蔽ゼロを1枚用意する**（`test_mechanics[28,0]` `sword_beast_arena`）。壁や水があると「敵が止まった/離れた」のが AI のせいか地形のせいか区別できない。
- **hp を積むのは「時間を進めるため」だけ。** gameover 中は `step()` が世界を止める＝そのあと来るモード交替が観測できない。難易度の主張には使わない。

### 7-5. ★ 「複数体で強すぎ」は構成を触る前に測る

剣獣5体の部屋（`dark_tower[1,2]`）は**構成を変えずに解決した**。判断は数字で行った（`.scratch/probe-dt12-pressure.mjs` / `probe-dt12-clear.mjs`）：
- 入口で 300 tick（36秒）立ち尽くしても「2セル以内に3体以上」が **0 回**（二相があるので囲まれない）／剣の間合いに敵が来た tick は 71/300＝**反撃の窓 24%**。
- **その時点で実際に取れる装備**で測る（世界に置いてあるのは木の剣 tier0 だけ＝`atk 4`・鎖かたびら `def 4`）。素直に殴るボットで5体を 54 tick・被弾3 で全滅できた＝「倒せない」は構成ではなく AI が原因。
- ∴脅威度の記録値（50.0）や柱を動かさずに済んだ。**構成を触ると `scripts/migrate-key-room-*.mjs` の `PREV_THREAT` と単調増加テストまで連鎖する**∴「強すぎ」と言われたら**まず AI と装備の実測**を疑う。
