# Blade of Lumia – 作業実行手順書（AI向け runbook）

> **このファイルの役割：** AI（あなた）がこのファイルを読んで、自律的に開発タスクを進めるための手順書。  
> ユーザーは「**WORKFLOW.md に従って進めて**」と言うだけでよい。  
> あなたは下記のフローに従って、次にやるべきことを自分で判断し、実行・記録する。
>
> 関連：`PLAN.md`（計画）/ `PROGRESS.md`（進捗ログ）/ `DECISIONS.md`（判断ログ）/ `IDEA.md`（アイデア）

## 🟢 デフォルトフロー：次タスクを進める

> ユーザーから特に指定がなければ、**このフローを実行する**。

### Step 1. 状況を把握する（読む）
1. **`PLAN.md` 冒頭の「🎯 実行キュー」を読み、未完（`[ ]`）の最小番号を次タスクに確定する。** これが実行順序の唯一の真実＝**他のファイルや過去ログを見て順序を決め直さない・ユーザーに「AとBのどちらをやるか」を尋ねない**（2026-07-28 ユーザー指摘）。
2. そのタスクについて `PLAN.md` の該当箇所（詳細）を読む
3. `PROGRESS.md` の「📍 現在地」は**参考メモとして**読む（そこに書かれた「次やること」は失効している可能性がある＝順序はキューが優先）
4. `DECISIONS.md` で関連する過去の判断を確認する（重複・矛盾を避けるため）
5. **⚠️ 記述の鮮度を疑う（着手前チェック・最重要）。** タスク記述は**書かれた時点のスナップショット**であって、その後ユーザーと協調して解決した結果が**上書きされずに残っている**ことがある（実際に 5.5i で発生＝下記「よくある失敗」）。着手前に必ず：
   - タスク記述が参照する「合格済み前例」「ユーザー確定事項」「既存の成果物（editor で作った盤面・実装済みの機構など）」を、**記述を信じずに一次ソースで裏取りする**（実マップの JSON・該当コミット・`DECISIONS.md` の後日の追記・`git --no-pager log` の日付）。
   - タスク記述の**日付**と、関連する `DECISIONS.md`/`PROGRESS.md` エントリの日付を比べる。**タスク記述より新しい判断があれば、そちらが優先**（古い記述は失効している）。
   - タスクが「◯◯を流用する」「◯◯で合格した語彙を使う」と書いていたら、**まずその◯◯そのものを開いて見る**。◯◯を見ずに、記述された抽象的方針（生成手順・不変条件など）から一から作り直そうとしていないか自問する。
   - **食い違いを見つけたら、実装に入る前にユーザーへ報告し、PLAN.md の古い記述を正す**（Step 4 の記録と同じ要領で、その場で修正して失効理由を1行残す）。「記述と現実が違うが記述に従う」は禁止。

### Step 2. 着手宣言する
- 「今から **Phase {番号}（{タスク名}）** を進めます」と一言で宣言する
- そのタスクに付いている推奨モデル（🧠 Opus / ⚡ Sonnet / 🧠→⚡）を確認する
  - **現在のモデルが推奨と食い違う場合**は、その旨をユーザーに伝える（切り替えを提案）
- 実装に入る前に「**何を・どう変えるか**」の方針を簡潔に説明する

### Step 3. 実装する
- PLAN.md の該当タスクのチェック項目に沿って実装する
- 大きいタスク（例：モジュール分割の各Step）は**1単位ずつ**進め、一度に詰め込まない
- **新機能を実装するとき：テストも必ず同時に設計・実装する（以下を参照）**
- 既存の挙動を壊していないか、テストで確認する
  - テストがある場合：Playwright / 単体テストを実行
  - テストが未整備の箇所：最低限の確認方法（手動手順や簡易チェック）を提示する

#### 🧪 新機能実装時のテスト原則

**「実装する前にテストを設計する」**。実装後に「どうテストするか」を考え始めると、
テストできない設計になっていたり、実際の動作を確認しない superficial なテストを書くことになる。

**テスト設計のチェックリスト（実装前に確認する）：**

1. **その機能が「動いた」と言える最低限の観測は何か？**
   - 状態変化（Set/フラグの変化）は `getStageState()` スナップショットで確認できるか？
   - DOM への反映（エフェクト）は `document.querySelector` で確認できるか？
   - ゲーム内部の生 Set/オブジェクトに直接アクセスできないなら `getProjectiles()` 等のスナップショット API に必要フィールドを追加する

2. **テスト用のパズル配置は、テストの手順で実際に到達できるか？**
   - ブーメランなら `maxRange`・`speed`・`MOVE_STEP` から最大到達距離を計算する
   - デフォルトの `heroDir='down'` に注意。`movePlayer('right')` 等で向きを変えてから使う
   - 距離が足りない場合はステージデータの配置を修正する（テストに合わせてパズルを作る）

3. **tick 数は根拠があるか？**
   - `速度 × MOVE_STEP × tick数 ≥ 必要距離` を計算して決める（「多めに回す」は根拠として不十分）

4. **テストは「合否が正しい理由で決まる」か？**
   - 意図した経路で状態が変化した場合のみ pass するか確認する
   - initLitTorches 等の「初期状態」に依存して「初めから成立している」テストになっていないか注意

**失敗したテストへの対処：**
- まず「ブーメランの実際の軌跡」など内部状態を tick ごとにログして原因を特定する
- `console.log` をテスト内に入れて `--reporter=line` で確認する
- 「フレーム数を増やせばパスする」ではなく根本原因を理解してから修正する

### Step 4. 記録する（完了時に必ず行う）
1. `PLAN.md` の完了したチェックボックスを `[x]` にする
2. **`PLAN.md` 冒頭「🎯 実行キュー」を更新する**＝終わった項目を `[x]`（日付付き・消さない）にし、作業中に判明した新タスクは**その場で番号を振って挿入し、なぜその位置かを1行書く**（「後で決める」「どちらでもよい」は禁止）
3. **⚠️ 失効した記述をその場で正す（古い記述を残さない・最重要）。** 作業中にユーザーと協調して方針が変わった／前提が覆った／既存の成果物で代替できると分かった場合、**その判断より前に書かれた記述（PLAN.md のタスク詳細・設計方針・残作業リスト・生成器やコードのコメント）を必ず更新する**。具体的には：
   - 覆された記述を**削除するか、「❌ 失効（YYYY-MM-DD・理由）」と明記して取り消し線的に残す**（残す場合も「今どうすべきか」を必ず併記する）。放置して次の自分/セッションが古い記述を鵜呑みにするのを防ぐ。
   - `DECISIONS.md` に「なぜ変わったか」を追記し、失効した PLAN 記述の場所を指しておく（相互リンク）。
   - **これは Step 1-5 の裏返し＝「古い記述を残す」問題を根絶するための対（つい）のルール。** 着手時に裏取り（Step 1-5）し、完了時に上書き（この項目）する。両方やって初めて記述が現実に追従する。
3. `PROGRESS.md` に新しいセッションログを追記する：
   - **やったこと** / **学び・気づき**（※「▶ 次やること」は書かない＝順序は実行キューだけが持つ）
4. `PROGRESS.md` の「📍 現在地」と「進捗サマリ」表を最新化する（現在地に書くのは**実行キューへのポインタ**と参考メモのみ）
5. 設計判断・ハマりどころがあれば `DECISIONS.md` に追記する

### Step 5. 完了報告する

以下の順番で報告する：

#### ① 実装サマリー
- 何を作ったか（新機能・変更点）を 3〜5 行で説明する

#### ② 試し方ガイド（新機能・ギミックを実装した場合は必須）
ユーザーがすぐにブラウザで確認できるよう、以下を提示する：
- **起動方法**（例：`npx vite outputs --port 18080`）
- **確認 URL**（`fromEditor=1` パラメータを使ったプレビューURLを具体的に記載）
- **操作手順**（ステップバイステップ。「どのキーを押すと何が起きるか」まで書く）
- URL が長い場合は `http://localhost:18080/blade-of-lumia/game/?<パラメータ>` の形で記載する

#### ③ コミットメッセージ案
下記「📝 コミットメッセージの作り方」に従って提示する。  
※ コミット操作そのものは**実行しない**（ユーザーが行う）

#### ④ 次タスクの推奨モデル
下記「🧠 次タスクのモデル推奨」に従って一言で報告する。

#### 🧠 次タスクのモデル推奨（コミットメッセージ案の後に必ず添える）
コミットメッセージ案を提示したら、続けて **「次にやるべきタスク」と「そのタスクに推奨するモデル」** を一言で報告する。判断手順：
1. 次タスクを特定する＝**`PLAN.md` 冒頭「🎯 実行キュー」の未完（`[ ]`）の最小番号**（他ファイルを見て決め直さない・複数候補を並べてユーザーに選ばせない）
2. そのタスク見出しの 🧠 Opus / ⚡ Sonnet / 🧠→⚡ を確認する
3. **🧠→⚡ のタスクは、設計が既に済んでいるかで実際の推奨を分ける：**
   - 設計（方針・変更箇所・データ構造）が `PLAN.md`/`DECISIONS.md` に**書き出し済み**なら → **⚡ Sonnet**（残りは機械的な実装）
   - 設計が**未着手**なら → **🧠 Opus でまず設計**（その後の実装フェーズで Sonnet に切替を提案）
4. 「現在のモデルが推奨と食い違う場合」は Step 2 と同様に切り替えを提案する
- **報告フォーマット例：**
  > 次は **Phase X-Y（タスク名）**。推奨モデルは **⚡ Sonnet**（設計は PLAN/DECISIONS に記載済みで、残りは実装のみのため）。

4. 次フェーズに進む前のリスク・前提を整理して提示する

### 🧪 分岐B：バグ修正 / 不具合対応

## 📏 共通ルール（全フロー共通）

- **モデル使い分け：** PLAN.md の各タスク見出しの 🧠/⚡/🧠→⚡ に従う
  - 🧠→⚡ は「設計フェーズ=Opus、実装フェーズ=Sonnet」で分けると効率的
- **Phase 0 完了までは新ゲーム機能を実装しない**（技術基盤を先に整える）
- **記録を怠らない：** 作業したら必ず PROGRESS.md を更新する（次回の自分のため）
- **迷ったら確認：** 判断に迷う・影響が大きい変更は、実行前にユーザーに確認する
- **⚠️ 記述は現実に追従させる（着手時に裏取り・完了時に上書き）：** タスク記述・設計方針・コメントは書かれた時点のスナップショットにすぎない。**ユーザーと協調して解決した結果を反映せず古い記述が残る**問題が散見される（Step 1-5／Step 4-3 で対処）。
  - **実例（2026-08-08〜09・5.5i）：** PLAN 5.5i は「dark_tower 4,3 を生成器で一から作る（二作業場 v2・幾何で I5 保証…）」と書いていたが、**この記述はユーザーが `test_mechanics 26,0` を editor で作って合格させる直前のもの**。26,0 成功後（PLAN 4.7・DECISIONS 2026-08-05）に「26,0 を流用する」で合意したのに 5.5i の古い記述が上書きされず残り、次セッションが 26,0 を見ずに生成器で袋小路（過剰な I5 で合格前例すら弾く盤面を延々測定）に入った。**教訓＝「◯◯を流用」系のタスクは、記述の手順を信じる前に◯◯の現物を必ず開く。**
- **⚠️ ファイル分割は「旧コード削除」までで1セット（最重要）：**
  - 大きいファイル（game.js / editor.js 等）から関数・コードを別ファイルに切り出すときは、
    **「新ファイルにコピー → テスト → 元ファイルの旧コードを削除 → 再テスト」までを必ず1タスク内で完結させる。**
  - 「コピー＋factory で上書き」しただけで元ファイルの旧本体を残すと、**同じロジックが2か所に重複し元ファイルが痩せない**（＝分割の目的が未達成）。
    実際にこの抜けが起き、game.js が分割後も 4075 行のまま残った（→ 0-2b で是正）。
  - 分割タスクの完了条件は「新ファイルができたこと」ではなく **「元ファイルの行数が実際に減ったこと」**。
    完了前に `wc -l` で元ファイルの行数減少を必ず確認する。

## 📝 コミットメッセージの作り方

> Step 5（完了報告）で、PROGRESS.md 更新と一緒にコミットメッセージ案を提示する。  
> **コミット操作は絶対に実行しない**（メッセージ案を作るだけ。コミットはユーザーが行う）。

以下のステップでコミットメッセージを作成する：

1. **まず `git status` を実行**して、変更されたファイルリストを確認する（**このステップは必ず最初に実施する**）
2. 各ファイルの差分を `git --no-pager diff`（必要に応じて未ステージ分も）で確認する
3. **`git status` に表示されたファイルの変更内容のみ**をメッセージに反映する
4. 他のファイルや以前のセッションの変更は**含めない**
5. **英語で、できるだけ簡潔に**。対象ファイル名は書かない（コミット情報に当然含まれるため）
6. コミットメッセージを**作成するだけ**。コミット操作は絶対にしない
7. 「今やった作業内容の記憶」だけでメッセージを作るのは避け、**必ずステップ1（git status）から始める**
8. **prefix + `: ` + サマリー** の形式にする（例：`feat: add xx feature` / `test: ...` / `fix: ...` / `refactor: ...` / `docs: ...` / `chore: ...`）

**フォーマット例：**
```
<prefix>: <簡潔なサマリー（英語）>

- 補足の箇条書き（任意・必要な場合のみ）
```

> ⚠️ `git` コマンドを使うときは **`git --no-pager ...`** を付け、ページャでインタラクションが止まらないようにする。

## 🌿 ブランチ運用（2026-08-13 ユーザー確定）

**作業ブランチは作らない＝`main` に直接コミット・直接 push する。** ユーザーが「コミットして」「push して」と言ったときの対象は `main`。

- **理由：** 開発者はユーザー1人（見るのは本人と家族のみ）＝レビューのための分岐に価値がない。実際、`docs/dungeon-5-ice-ruins-design`（2026-06-27 にダンジョン5設計の1タスク用に切ったブランチ）を畳まないまま **211コミット・2か月ぶんの開発が全部そこに溜まり、`origin/main` が2か月前の姿のまま公開されていた**。2026-08-13 に `main` へマージ＋push して解消（`beefdf1`）。
- **⚠️ push すると本番サイトに公開される**（リポジトリ直下の `vercel.json`・production ブランチが `main`）。∴ push は「公開」と同義だと自覚して実行する。作りかけを出したくない場合はユーザーに確認する。
- **相変わらず自発的にはコミットしない。** 上記「コミットメッセージの作り方」のとおり Step 5 では**メッセージ案の提示まで**＝ユーザーが「コミットして」と言ってから実行する（ブランチ運用が変わっても、この境界は変わらない）。
